# Light/Dark Mode Switch in the Header

## Goal
Add a manual light/dark mode toggle to the header. Backlog source:
`.plan/000-backlog.md`: *"Add light mode/ dark mode switch in the header."*

Today the app has no manual control — it only ever follows the OS/browser's
`prefers-color-scheme`, via a single `@media (prefers-color-scheme: dark)`
block in `web/src/styles/setup/variables.css` that redefines every color
token. This plan adds an explicit override on top of that, without removing
the automatic system-following behavior for anyone who never touches the
toggle.

## Scope
- Frontend-only (`web/`). No `api/` changes — the preference is a
  browser/device setting, not account data (no `user` column exists or is
  being added for it; consistent with `session-storage.service.ts` already
  using `localStorage` for a client-only preference).
- In scope: the toggle control, its placement in `web/src/App.vue`'s header,
  the persistence mechanism, and the CSS override layer in
  `web/src/styles/setup/variables.css`.
- Out of scope: a three-way "system / light / dark" selector — the backlog
  says "switch," i.e. two states. See Assumptions for how "no explicit choice
  yet" is still handled (it isn't a third *stored* state, it's just "nothing
  stored").

## Assumptions
- **Token structure**: `variables.css` currently has `:root { …light values… }`
  followed by one `@media (prefers-color-scheme: dark) { :root { …dark
  values… } }` block. To let an explicit choice override the system
  preference in either direction, this becomes three blocks: `:root { …light
  values… }` (unchanged, the default), `@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { …dark values… } }` (system-dark still
  applies automatically unless the user explicitly chose light), and a new
  `:root[data-theme="dark"] { …dark values… }` outside any media query (so an
  explicit dark choice applies even when the system is light). This is the
  standard pattern for a manual override layered on top of a media-query
  default and touches no token *values*, only which selector reaches them.
- **Persistence**: `localStorage`, one key, values `'light'`/`'dark'`. No
  stored value at all means "follow the system," which is today's behavior
  and needs no code to preserve — it's simply what happens when
  `data-theme` is never set.
- **No flash of the wrong theme on load**: a small inline `<script>` in
  `web/index.html`'s `<head>` (before any CSS or Vue code runs) reads the
  stored preference and sets `document.documentElement.dataset.theme`
  synchronously, before first paint. This has to be a plain inline script,
  not something `main.ts` does after Vue mounts — by then the first frame
  has already painted in the wrong theme.
- **Visible whether signed in or not.** Unlike `SettingsMenu.vue` (gated
  behind `auth.isAuthenticated` — `web/src/App.vue:36`), a color-scheme
  preference isn't account-specific and should work for a signed-out visitor
  on `/login` too. Placed in the header outside that `v-if` block.
- **Toggle target, not tri-state control**: clicking it always sets an
  explicit `light` or `dark` value (flipping from whatever is *currently
  rendered* — checking `window.matchMedia('(prefers-color-scheme:
  dark)').matches` at click time when nothing is stored yet, not assuming
  light). There's no "clear my override, go back to following the system" UI
  in this plan — the backlog asked for a switch, not a three-way selector.
  Flag this as an easy follow-up if wanted later.
- **Test environment gap**: no test in `web/` currently mocks
  `window.matchMedia` — jsdom doesn't implement it by default, so any test
  touching this feature needs a stub (`Object.defineProperty(window,
  'matchMedia', ...)` returning a minimal `MediaQueryList`-shaped object) or
  it throws `matchMedia is not a function`. Not present anywhere in the repo
  today; whoever implements this adds the first one.

## Open Questions
None — the toggle's behavior (explicit two-state override on top of the
existing system-preference default) is fully specified above.

## Steps
1. `web/index.html`: add a small inline `<script>` in `<head>`, before the
   `main.ts` module script, that reads the stored theme key from
   `localStorage` and sets `document.documentElement.dataset.theme` if it's
   `'light'` or `'dark'` — a no-op (leaves the attribute unset) if nothing is
   stored, so system preference still applies. Keep this script tiny and
   dependency-free (it runs before Vue, Pinia, or any module is loaded).
2. `web/src/styles/setup/variables.css`: restructure the dark block as
   described in Assumptions — add `:not([data-theme="light"])` to the
   existing `@media` selector, and add a new `:root[data-theme="dark"]`
   block with the same dark values, outside the media query.
3. New `web/src/services/theme.service.ts`: a small, pure module (mirrors
   `session-storage.service.ts`'s shape) with `getStoredTheme()`,
   `setStoredTheme(theme)`, and `getSystemTheme()` (reads
   `matchMedia('(prefers-color-scheme: dark)').matches`). No Vue
   reactivity here — just the localStorage/DOM/matchMedia mechanics, unit
   testable in isolation.
4. New `web/src/stores/theme.store.ts` (Pinia, matching the existing
   `auth.store.ts`/`interview.store.ts` convention): a reactive `theme` ref
   initialized from `document.documentElement.dataset.theme` (already set by
   the inline script, so this store doesn't re-derive it from scratch — one
   source of truth) or `getSystemTheme()` if unset, and a `toggleTheme()`
   action that flips it, writes the new value via `setStoredTheme`, and sets
   `document.documentElement.dataset.theme` to match.
5. `web/src/App.vue`: add a toggle button in the header (outside the
   `auth.isAuthenticated` block), `Sun`/`Moon` from `lucide-vue-next`
   swapping with state, `aria-label` that names the action ("Switch to dark
   mode"/"Switch to light mode"), calling `themeStore.toggleTheme()`.
6. Styling for the new button under `web/src/styles/cmps/` (extend
   `menu.css` if the settings-menu-trigger button's existing `.btn-ghost`-
   style pattern already covers it, otherwise a small addition) — tokens
   only, no inline styles.

## Validation
- `cd web && npm test && npx vue-tsc --noEmit && npm run lint` — new tests
  cover: `theme.service.ts`'s three functions in isolation (including a
  `matchMedia` mock); `theme.store.ts`'s `toggleTheme()` flips state, persists
  it, and sets the DOM attribute; the header button renders on both an
  authenticated and signed-out (e.g. `/login`) render, toggles the
  `aria-label`/icon with state, and clicking it doesn't navigate or submit
  anything.
- Manual: `npm run dev`, toggle the switch, confirm the whole app re-colors
  immediately; reload the page and confirm the choice persisted (no flash of
  the previous theme before it settles); clear the stored preference (or use
  a fresh profile) and confirm the app still follows the OS-level dark/light
  setting with no toggle interaction.

## Risks
- Forgetting the inline `<head>` script (Step 1) and only setting
  `data-theme` from within `main.ts`/Pinia would reintroduce exactly the
  flash-of-wrong-theme problem this plan exists to avoid — verify by testing
  with DevTools' network throttling or a hard reload, not just a warm cache.
- A test that exercises `theme.service.ts`/`theme.store.ts` without stubbing
  `window.matchMedia` will throw, not silently pass — make sure the stub
  lands before the assertion, not after.

## Rollout Order
1. `variables.css` restructuring + `index.html` inline script (the
   mechanism, with nothing wired to it yet — the app should behave
   identically to today at this point, since nothing sets `data-theme`).
2. `theme.service.ts` + `theme.store.ts` + the header button.
3. QA pass, including the manual flash/persistence/system-fallback checks
   above.

## Rollback
Additive and self-contained — revert the branch's merge commit to remove the
toggle, the store/service, and the CSS override selectors; the existing
system-preference-only behavior returns untouched since its own selectors are
never deleted, only extended.
