# UI Fixes: Show Password, Card Animations, Thin Scrollbars

## Goal
Three small, independent UI polish fixes. Backlog source: `.plan/000-backlog.md`:
*"UI fixes: 1. In User settings: Add a show password option for the password
field. 2. Add animations for the cards in 'home' and 'practice' routes. 3.
change the scrollbars to be thinner with colors that fit the theme."*

## Scope
- Frontend-only (`web/`). No `api/` changes.
- In scope:
  1. `web/src/views/UserSettingsView.vue` — a show/hide toggle on its password
     field(s).
  2. `web/src/views/HomeView.vue` and `web/src/views/SetupView.vue` — an
     entrance animation on their `.card` elements.
  3. A global, theme-aware thin scrollbar, app-wide.
- Out of scope: `LoginView.vue`'s password field (the backlog item names "User
  settings" specifically, not the login/signup form — the two are separate
  screens with separate forms); any card outside `HomeView.vue`/`SetupView.vue`
  (`ReportView.vue`, `LoginView.vue`, `EvaluationCard.vue`, etc. weren't named).

## Assumptions
- **Show password: two independent toggles, not one.** `UserSettingsView.vue`
  has two password inputs — "Current password" and "New password" — read at
  `web/src/views/UserSettingsView.vue:190-215`. The backlog says "the password
  field" (singular) but there are two on this form; the reasonable reading is
  both get the same treatment, each toggled independently (revealing the
  current password shouldn't force-reveal the new one, or vice versa) — one
  shared toggle would be a worse, more surprising UX for no benefit.
- **Animation: a fade + slight-rise entrance, staggered for repeated cards.**
  `HomeView.vue` has two lists of repeated `.card` elements (`.home-step`,
  `.home-feature` — `web/src/views/HomeView.vue:123,135`) plus the hero card;
  `SetupView.vue` has exactly one `.card` (the form,
  `web/src/views/SetupView.vue:62`). List items get a staggered delay (each
  card slightly after the previous) so they read as a sequence, not a flash;
  the single `SetupView.vue` card just animates in on its own. This already
  respects reduced-motion for free — `web/src/styles/setup/reset.css:36-43`
  globally forces `animation-duration: 0.01ms` under
  `prefers-reduced-motion: reduce`, so no per-animation opt-out is needed.
  Home's accordion sections (`AccordionSection.vue`, added in plan 008) are not
  themselves `.card` elements and are unaffected — their own open/close
  animation is a separate, already-shipped concern.
- **Scrollbar: global, both engines.** `scrollbar-width`/`scrollbar-color` for
  Firefox and `::-webkit-scrollbar*` for Chromium/Safari/Edge, using existing
  design tokens so it inherits the dark-mode palette automatically (every
  color token in `web/src/styles/setup/variables.css` already has a
  `prefers-color-scheme: dark` override — the scrollbar rule should reference
  tokens, never hardcode a color, so it doesn't need its own dark-mode block).
  No existing scrollbar CSS exists anywhere in `web/src/styles/` (confirmed by
  search) — this is new, not a fix to something broken.

## Open Questions
None — all three fixes are small enough that the Assumptions above fully
specify the intended behavior; revise this plan if any assumption doesn't
match what's wanted once seen.

## Steps
1. `web/src/views/UserSettingsView.vue`: add a per-field show/hide toggle
   (`Eye`/`EyeOff` from `lucide-vue-next`, `type="button"` so it never submits
   the form, `aria-label="Show password"`/`"Hide password"` that flips with
   state) to both the "Current password" and "New password" fields. Toggling
   switches that input's `type` between `password` and `text`. Two independent
   `ref`s (one per field), not one shared boolean.
2. New stylesheet or an addition to an existing one under
   `web/src/styles/cmps/` (e.g. extend `form.css` if a `.field` pattern
   already lives there, otherwise a small addition) for the toggle button's
   positioning (inside the input, right-aligned) — tokens only, no inline
   styles, per `.claude/rules/ui-and-styling.md`.
3. New CSS keyframes (e.g. `card-in`: opacity 0→1, `translateY` a small
   amount → 0) added under `web/src/styles/cmps/card.css` or a new
   `web/src/styles/cmps/animation.css` imported from `cmps/index.css`. Apply
   to `HomeView.vue`'s hero card, `.home-step` cards (staggered), `.home-
   feature` cards (staggered), and `SetupView.vue`'s form card. Stagger via
   `animation-delay` computed from each `v-for` item's index (inline `:style`
   binding is acceptable here since the delay is genuinely per-instance data,
   not a static value — this isn't the inline-*styling* the styling rule
   forbids, it's a computed per-item animation-timing value; keep every other
   property in the CSS class).
4. Global scrollbar rule — add to `web/src/styles/basics/base.css` (or
   wherever the project's existing global/body-level rules live, check that
   file's current contents first): `scrollbar-width: thin` and
   `scrollbar-color: var(--clr-border) transparent` on `html` (or `:root`),
   plus `::-webkit-scrollbar` (width ~8-10px), `::-webkit-scrollbar-track`
   (transparent or `var(--clr-bg)`), `::-webkit-scrollbar-thumb` (`var(--clr-
   border)`, `border-radius: var(--radius-pill)`, and a `:hover` state using
   `var(--clr-text-muted)` or `var(--clr-accent)` — pick whichever reads as
   "hover feedback" rather than "error state" once seen).

## Validation
- `cd web && npm test && npx vue-tsc --noEmit && npm run lint` — new/updated
  tests cover: `UserSettingsView.spec.ts` — each password field's toggle
  switches its own `input[type]` between `password`/`text` independently
  (toggling one doesn't affect the other), and the toggle button doesn't
  submit the form (no `type="submit"` fallback, no navigation on click). Card
  animation and scrollbar styling are presentational CSS with no interactive
  behavior to unit test — cover them with a smoke assertion that the expected
  classes are present (e.g. `HomeView.spec.ts` still finds the expected
  `.card`/`.home-step`/`.home-feature` elements after this change, so a class
  rename didn't silently break existing content assertions) rather than
  testing computed animation values, which jsdom doesn't render anyway.
- Manual: `npm run dev`, confirm on `/` and `/practice` the cards visibly
  animate in on load (and don't if the OS's reduce-motion setting is on),
  confirm both password fields on `/settings` toggle independently, and
  confirm scrollbars are visibly thinner and theme-colored in both light and
  dark mode (OS/browser dark mode toggle) on any page long enough to scroll.

## Risks
- A poorly-tuned animation (too slow, too much delay stacked across many
  `.home-feature` cards) reads as sluggish rather than polished — keep total
  stagger short (e.g. cap delay per item, don't let a 7-item feature list take
  a full extra second to finish appearing).
- `::-webkit-scrollbar` styling has no Firefox equivalent beyond
  `scrollbar-width`/`scrollbar-color` (already covered) — no further risk, just
  confirming both codepaths are addressed so no browser is left with the
  default chrome.

## Rollout Order
1. Show-password toggle (`UserSettingsView.vue` + its tests).
2. Card entrance animation (`HomeView.vue`, `SetupView.vue` + styles).
3. Global scrollbar styling.
4. QA pass, including the manual light/dark + reduced-motion checks above.

## Rollback
Purely additive/presentational CSS and a self-contained UI toggle — revert the
branch's merge commit to remove all three with no data or API surface touched.
